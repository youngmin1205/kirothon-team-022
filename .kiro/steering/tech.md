# 기술 스택 & 코딩 컨벤션

> 아이디어와 무관하게 **확정된** 스택이다. 당일 다시 논의하지 않는다.
> 실측 근거: `docs/kiro-env.md`

## 런타임 (메이저 버전 고정, 패치 자유)

| 도구 | 무엇인지 | 버전 |
|---|---|---|
| Node.js | JavaScript 실행 환경 | 26 LTS (깨지면 24) |
| `pnpm` | Node 라이브러리 패키지 매니저 | 최신 |
| Python | 백엔드 실행 환경 | 3.14 (하한 3.12 — 팀원 PC 사정) |
| `uv` | Python 라이브러리·가상환경 관리 | 최신 |
| AWS CLI | AWS 를 터미널에서 조작 | v2 |
| kiro-cli | Kiro 에이전트 실행 | **3.2.1 이상** (2.x 와 훅 포맷·권한 필드·도구 이름이 다르다) |

## 애플리케이션

| 레이어 | 확정 | 무엇인지 | 왜 |
|---|---|---|---|
| 프런트 | **React 19** | 화면을 컴포넌트로 조립 | 담당3 목업을 거의 그대로 옮겼다 |
| | **Vite** | 개발 서버 + 빌드 도구 | 고치면 즉시 화면에 반영된다 |
| | **TypeScript** | 타입을 붙인 JavaScript | API 형식 불일치를 컴파일 때 잡는다 |
| 백엔드 | **FastAPI** | Python 웹 API 프레임워크 | 코드가 짧고 타입 검증이 기본이다 |
| | **uvicorn** | FastAPI 를 띄우는 서버 | 표준 조합 |
| LLM | **Bedrock Converse API** (boto3 로 직접 호출) | AWS 의 LLM 호출 방식. 모델을 바꿔도 코드가 같다 | 에이전트 프레임워크를 추가하지 않는다. 당일 디버깅할 미지의 레이어를 늘리지 않는다 |
| 상태 | 프로세스 메모리 | — | DB 를 붙여서 얻는 게 없다. 재시작하면 날아가는 것이 유일한 단점이고 데모에서는 문제가 아니다 |
| 배포 | 로컬 실행 | — | URL 이 필요해지면 터널로 2분. EC2 는 그다음 |

검사 도구: Python 은 `ruff`(규칙)·`pytest`(테스트), 프런트는 `oxlint`·`vitest`.
`concurrently` 가 `pnpm dev` 에서 두 서버를 동시에 띄운다.
`Playwright` 는 브라우저를 코드로 조작해 화면을 검증하고 영상을 녹화한다(담당3, macOS).

**기본 아키텍처는 화면 → API → 에이전트 루프 → Bedrock 이다.**

## 실행 (이 명령만 쓴다)

```bash
pnpm bootstrap    # 처음 한 번. 라이브러리 설치 (277MB)
pnpm dev      # 입력창으로 직접 대화하며 개발 (실제 모델 호출)
pnpm mock     # 고정 시나리오 재생 (Bedrock 호출 없음) → localhost:5173
pnpm smoke    # 데모가 끝까지 도는지 자동 확인
pnpm check    # lint · 타입 · 테스트
```

`pnpm bootstrap` 은 `uv sync`(Python) + `pnpm -C frontend install`(Node) 을 한 번에 돌린다.
발표 산출물 도구는 `pnpm bootstrap:deliverables` 로 따로 받는다 (1.7GB, macOS 전용, 담당3만).

포트는 백엔드 8000, 프런트 5173 으로 고정이다. 바꾸지 않는다 — 녹화 설정과 검증 스크립트가 이 값을 쓴다.

## mock 우선 (중요)

- `USE_MOCK=1` 이면 Bedrock 을 호출하지 않고 `backend/features/<기능>/mock.json` 의 구간을 순서대로 재생한다
- 탐색과 화면 작업은 mock 으로 한다. 크레딧과 throttling 을 아낀다
- **mock 은 고정 경로다.** 입력창에 자유롭게 쳐 보는 것은 `pnpm dev` 로 한다. mock 모드에서 자유 입력을 보내면 대본이 진행되지 않고 안내가 돌아온다
- 실제 호출이 실패하면 코드가 예외를 던지지 않고 mock 으로 떨어진다. **데모 중 화면이 죽는 것이 가장 나쁜 결과다**
- 새 기능을 만들 때 mock fixture 를 먼저 쓴다. 그러면 화면을 백엔드 없이 끝까지 만들 수 있다

## 코딩 컨벤션

- TypeScript: 함수형 컴포넌트, named export, 타입 명시. `any` 지양
- Python: 타입 힌트 사용, `ruff` 기준, 함수는 작게
- 폴더는 기능 단위로 묶는다 (레이어보다 기능 우선)
- 주석은 "왜"를 적는다. "무엇"은 코드로 드러낸다

## 보안

- AWS 키·토큰·시크릿은 코드·로그·커밋에 **절대** 넣지 않는다. `.env` + 환경변수만
- 커밋 전 `./scripts/scan-secrets.sh` 가 걸러낸다
- Bedrock 호출은 `backend/core/bedrock.py` 래퍼로만 한다
- 자격증명은 프로필 → 환경변수 키 → 인스턴스 역할 순으로 boto3 기본 체인에 맡긴다. 코드에서 분기하지 않는다
- 사용자 입력은 신뢰 경계에서 검증한다

## 하지 말 것

- 요청하지 않은 대규모 리팩터
- 임의 의존성 추가 (먼저 팀에 공유)
- `git push --force`, 남의 담당 폴더 임의 수정
- 데모에 불필요한 과한 추상화 (해커톤은 속도 우선)
- 포트·`#play` id·구간 신호(`data-beat`) 변경 — 검증과 녹화가 깨진다

## 테스트

- 단발 실행만 (`pytest`, `vitest --run`). watch 모드 금지
- 새 기능에는 "데모 구간이 순서대로 완료되는가" 테스트 하나면 충분하다
- 통합 체크포인트마다 `pnpm smoke` 를 돌린다. 통과한 상태만 커밋한다
