## 데모 구간 (가장 중요)

> 여기서 "데모"는 제품의 **핵심 사용 흐름(happy path)** 을 말한다. 사용자가 앱을 열어서
> 끝까지 가는 경로를 단계로 쪼갠 것이다. 코드와 녹화 도구에서는 `beat` 라고 부른다.
>
> **이걸 먼저 정하는 이유는 서로 기다리지 않기 위해서다.** 단계 이름과 문구가
> `mock.json` 에 먼저 들어가면, 프런트는 백엔드 로직 없이 화면을 끝까지 만든다.

흐름은 `#play` 버튼 하나로 처음부터 끝까지 자동 재생되어야 한다. 아래 단계 id 가
**네 곳에서 같은 이름으로 쓰인다.** 그래서 여기만 정하면 나머지가 따라온다.

| 쓰이는 곳 | 어떻게 |
|---|---|
| 화면 | `data-beat="<id>"` + `data-state="pending\|active\|done"` |
| 서버 | `backend/features/<기능>/mock.json` 의 `beats[].id` |
| 자동 검증 | `pnpm smoke` 가 구간이 순서대로 done 이 되는지 확인 |
| 영상·슬라이드 | `deliverables/product.md` 의 `capture.beats[].id` |

구간은 6~8개로 한다. 더 많으면 데모가 길고, 적으면 이야기가 안 된다.

**이 표를 먼저 채우고 `mock.json` 에 단계별 문구를 넣으면, 기능이 하나도 없는
상태에서도 흐름이 완주한다.** 그러면 프런트가 백엔드를 기다리지 않는다.

> 한계: 이 구조는 순차적인 흐름을 가정한다. 대시보드형이나 배치 처리형이면
> 억지가 되므로 느슨하게 쓰거나 버린다.

`사용자 발화` 는 그 구간 직전에 사용자가 하는 말이다. `mock.json` 의 `say` 가 되고, live 녹화에서
`#play` 가 이 문장을 실제 모델에 보낸다. 1번은 시작 화면이라 비운다.

## 당일 고정 규칙 (아이디어와 무관)

아래는 주제가 무엇이든 지킨다.

- **데모 경로 하나를 끝까지 완주시키는 것이 최우선이다.** 곁가지 기능보다 완주가 먼저다
- **mock 은 비상용이다.** `USE_MOCK=1` 로 Bedrock 없이 전 구간이 재생되어야 한다.
  최종 녹화는 live(실제 모델)로 하고, 실패하면 mock 으로 대체한다. 무대 시연은 mock 으로 한다
- **`mock.json` 의 구간마다 `say`(사용자 발화)를 채운다.** live `#play` 가 이 문장을 모델에 보낸다
- **통합 체크포인트에서 데모가 돌아야 한다** (11:30 / 13:00 / 15:30 / 16:30).
  안 돌면 기능을 더 붙이지 않고 그것부터 고친다
- **17:00 이후 기능 추가 중단.** 버그와 데모 안정화만
- 범위를 줄이는 결정은 lead 가 한다. 에이전트가 임의로 기능을 늘리지 않는다
