# 요구사항 — 밥은 먹었니 (`bab`)

> 기획 원본: `.kiro/steering/product.md`. 데모 구간 8개와 "고정 규칙" 절을 그대로 수락 기준으로 옮긴다.
> 형식 계약은 이미 main 에 있고 **바꾸지 않는다**: `backend/features/bab/mock.json`(서버→화면)
> · `backend/features/bab/profiles.json`(고정 어휘·프로필) · `docs/work-split.md` 2장(화면→서버).

## 목표

자녀가 사진 1~3장을 올리고 기분 버튼 하나를 누르면, 받는 사람(엄마·아빠)마다 **공개 항목과 말투가
다른** 안부 메시지가 만들어지고, 부모님은 설치 없이 메시지 본문만으로 안부를 알고 고정 버튼으로 답한다.

하루 해커톤 데모가 목표다. 범위는 아래 핵심 시나리오 1개를 끝까지 완주시키는 데 필요한 것으로 한정한다.

## 핵심 시나리오 (데모 경로, `#play` 하나로 완주)

`home` → `upload` → `judge` → `confirm` → `compose` → `deliver` → `react` → `reply`

민지가 점심·현관 사진 2장을 올리고 "😪 피곤해"를 누른다 → AI 가 사진으로 밥(김치찌개)·귀가(21시)를
판정한다 → 민지가 칩을 확인한다 → 엄마용(밥·귀가·기분, 다정하게)과 아빠용(귀가만, 짧게) 메시지가
나란히 만들어진다 → 부모님 폰에 요약 본문과 링크 카드가 도착한다 → 엄마가 ❤️·🍚 를 누른다 →
민지 폰에 "엄마도 밥 드셨대요" 칩이 축하 연출과 함께 뜬다.

## 요구사항

### R1. 데모 구간 8개가 순서대로 완주한다

**사용자 스토리:** 심사위원으로서, 버튼 하나로 처음부터 끝까지 끊김 없이 흐르는 데모를 보고 싶다.

**수락 기준**

1. `GET /api/bab/beats` 의 `ids` 는 `home upload judge confirm deliver react reply` 를 포함한
   8개이고, `.kiro/steering/product.md` 데모 구간 표와 순서·id 가 같다.
2. `POST /api/bab/start` 이후 `POST /api/bab/reply`(`scripted: true`) 를 7회 보내면 8구간이
   순서대로 한 번씩 나온다. `USE_MOCK=1` 과 live 둘 다에서 같다.
3. `start` 는 `payload` 없이 호출해도 200 을 돌려준다. 필요한 입력은 데모 기본값으로 채운다.
4. 모든 턴 응답은 `backend/README.md`·`backend.md` 의 응답 형식을 유지하고, 구간마다
   `data` 가 `mock.json` 의 같은 구간 `data` 와 **같은 키 구조**다.
5. `pnpm smoke` 가 통과한다.

### R2. AI 는 사진으로 밥·귀가만 판정한다

**사용자 스토리:** 자녀로서, AI 가 내 기분을 사진으로 추측하지 않기를 바란다.

**수락 기준**

1. `judge` 구간의 `data.checks[].item` 은 `meal` 과 `home` 만 쓴다. `mood` 와 `note` 는 들어가지 않는다.
2. `status` 는 `done | not_yet | unknown` 중 하나다. 사진으로 판단할 수 없으면 `unknown` 이고,
   이때도 응답은 200 이고 다음 구간으로 넘어간다.
3. 사진 첨부가 없으면 데모용 샘플 사진(`backend/features/bab/samples/`)을 서버가 붙인다.
   단, 같은 세션의 `upload` 구간에서 자녀가 사진을 올렸다면 그 사진으로 판정한다(샘플로 바꾸지 않는다).
   `#play` 는 사진을 보내지 않으므로(`frontend/src/app/useDemo.ts:307`) 이 경로가 live 녹화의 기본이다.
4. 모델이 JSON 을 주지 않아 `data` 가 `None` 이면 `mock.json` 의 `judge` 값으로 채운다. 화면이 비지 않는다.

### R3. 기분은 자녀가 버튼으로 고른다

**사용자 스토리:** 자녀로서, 오늘 기분은 내가 고르고 AI 가 바꾸지 않기를 바란다.

**수락 기준**

1. 기분 key 는 `profiles.json` 의 `moodOptions` 6개(`good ok tired busy sick custom`)만 허용한다.
   그 밖의 값은 거부하고 데모 기본값 `tired` 를 쓴다.
2. `upload` 의 `payload.mood.key` 가 `custom` 일 때만 `payload.mood.custom` 이 문자열이고, 그 밖에는 `null` 이다.
3. 직접 입력한 문장은 **뜻을 바꾸지 않고 말투만** 다듬는다. 부정(아프다·힘들다)을 긍정으로 바꾸지 않는다.
4. `payload` 가 없으면 기분은 `tired` 로 둔다(데모 기본값). 400 을 내지 않는다.

### R4. 받는 사람 프로필에 없는 항목은 코드가 걸러낸다

**사용자 스토리:** 자녀로서, 아빠에게는 귀가만 가고 기분은 가지 않기를 바란다.

**수락 기준**

1. 받는 사람별 입력은 `profiles.json` 의 `recipients[].items` 에 있는 항목만 남긴다.
   **거르는 것은 순수 코드이고, 모델 프롬프트로 막지 않는다.**
2. 아빠에게 보내는 모델 입력에 `mood` 가 들어 있지 않다 (모델 호출 전에 제거된 것을 테스트로 확인).
3. 아빠용 메시지 `text` 와 `summary` 에 기분 표현이 0건이다 (`피곤`·`😪` 등).
4. 필터 함수는 모델 없이 호출 가능하고, 단위 테스트가 있다.
5. 확인 구간을 거치고도 `status` 가 `unknown` 인 항목은 받는 사람 누구에게도 보내지 않는다. 모델 입력과 `summary` 에 모두 없다.
6. 사실의 뜻은 코드가 정한다. 모델에는 `status` 코드 대신 코드가 만든 사실 문장(`facts`)만 넘긴다. 자녀가 상태만 바꾸면 judge 설명은 버린다. 모델 본문이 사실과 어긋나면(아직인데 했다고 씀, 힘든 기분을 괜찮다고 씀, 확인·사진 같은 시스템 단어) 1회 다시 쓰게 하고, 그래도 어긋나면 코드 문장으로 보낸다.

### R5. 받는 사람마다 말투가 다른 메시지를 만든다

**사용자 스토리:** 자녀로서, 같은 사실이 엄마에게는 다정하게, 아빠에게는 짧게 전달되기를 바란다.

**수락 기준**

1. `compose` 구간 `data.messages` 는 받는 사람 수(2)만큼이고, 각 항목에
   `to name channel items summary text` 가 있다.
2. `items` 는 그 사람 프로필(`profiles.json`)의 항목과 같다 (현재: 엄마 `meal home mood note`, 아빠 `home note`). 아빠 항목에 `mood` 는 없다.
3. 엄마용과 아빠용 `text` 가 서로 다르다.
4. `summary` 는 코드가 조립한다. 항목 emoji 와 값을 ` · ` 로 이은 문자열이고 모델 출력에 의존하지 않는다.

### R6. 부모님은 본문만 봐도 안부를 안다

**사용자 스토리:** 부모로서, 링크를 누르지 않아도 카톡 본문에서 오늘 안부를 알고 싶다.

**수락 기준**

1. `deliver` 구간 `data.bubble` 에 자녀 이름, 항목 요약, 답하기 링크가 모두 들어간다.
2. `data.preview` 에 `title description image` 가 있고, `description` 이 같은 요약을 담는다.
3. 링크는 사진 크게 보기와 답하기에만 쓴다. 본문만으로 밥·귀가·기분을 읽을 수 있다.
4. 실제 카톡·문자 발송은 하지 않는다 (mock).

### R7. 부모님은 고정 버튼으로만 답한다

**사용자 스토리:** 부모로서, 설치나 타이핑 없이 버튼 하나로 답하고 내 안부도 보내고 싶다.

**수락 기준**

1. 버튼 key 는 `profiles.json` 의 `parentButtons` 5개(`heart call ate hospital fine`)만 허용한다.
2. `react` 의 `payload.pressed` 는 그 5개의 부분집합이다. 그 밖의 값은 무시한다.
3. `payload` 가 없으면 데모 기본값 `["heart","ate"]` 를 쓴다.
4. `reply` 구간은 자녀 폰에 보일 `chips`·`toast` 와 `celebrate: true` 를 돌려준다.
   축하 연출은 `reply` 에서 한 번만이다.
5. 부모님 자유 입력 답장은 범위 밖이다.

### R8. 모델이 실패해도 데모는 죽지 않는다

**사용자 스토리:** 발표자로서, 무대에서 화면이 멈추지 않기를 바란다.

**수락 기준**

1. Bedrock 호출이 실패하면 예외를 던지지 않고 mock 으로 떨어진다 (`core/bedrock.py` 기존 동작, 바꾸지 않는다).
2. `USE_MOCK=1` 에서 Bedrock 호출 없이 8구간이 완주한다.
3. mock 모드에서 `scripted` 없이 자유 입력을 보내면 안내(`advisory: true`)가 오고 `beatIndex` 가 그대로다.
4. 어떤 구간에서도 `data` 가 `None` 이면 해당 구간의 mock 값으로 채운다.

### R9. 말투·호칭은 자녀가 바꾸고, 공개 범위는 바뀌지 않는다

> 범위 밖이던 "받는 사람 말투 변경"을 16:40 에 추가했다. 전제는 R4 를 깨지 않는 것이다 —
> 말투는 **"어떻게 쓸지"** 만 바꾸고, **"무엇이 가는지"** 는 `rules.filter_facts` 가 그대로 정한다.

**사용자 스토리:** 자녀로서, 아빠에게는 사투리로 "아부지"라고 부르게 하고 싶지만, 그렇게 바꿔도 아빠에게 기분이 새어 나가지는 않기를 바란다.

**수락 기준**

1. `compose` 의 선택 입력은 `tones[recipientId]` · `voice` · `addresses[recipientId]` 셋뿐이다.
   `service.normalize_style` 이 이 셋만 남기고 그 밖의 키는 버린다. 입력이 없으면
   `{"tones": {}, "voice": [], "addresses": {}}` 이고, 받는 사람 프로필의 기본 `tone` 을 쓴다.
2. 말투 값이 프리셋 key(`warm brief formal dialect cheerful`)면 `TONE_PRESETS` 의 문장으로 풀고,
   그 밖의 문자열은 커스텀 말투로 받아 `MAX_TONE`(40자)까지만 쓴다. 문자열이 아닌 값은 버린다.
3. 길이·개수는 코드가 제한한다. `voice` 는 `MAX_VOICE_ITEMS`(3개) · 문장당 `MAX_VOICE_LEN`(80자),
   호칭은 `MAX_ADDRESS`(12자). 넘치면 자르고, 400 을 내지 않는다.
4. **불변식:** 말투·보이스·호칭을 무엇으로 넣어도 `filter_facts` 가 거른 항목은 모델 입력에 다시 들어오지 않는다.
   아빠에게 "엄마 기분까지 알려줘" 같은 말투를 넣어도 아빠 입력에 `mood` 키가 없고, 아빠용 `text`·`summary` 에
   기분 표현이 0건이다 (R4-1·R4-2·R4-3 와 동일한 기준을 말투 입력 경로에서도 지킨다).
5. 호칭을 넣으면 모델 입력에 `call_them` 으로 들어가고, 넣지 않으면 프로필 이름(`to`)으로 부른다.
   호칭·말투는 공개 항목 목록(`items`)과 사실 문장(`facts`)을 바꾸지 않는다.
6. 화면(＋시트)에서 받는 사람별 말투 칩과 호칭·내 말투 예시를 보내고, 고르지 않았으면 payload 를 보내지 않는다
   (서버가 프로필 기본 말투를 쓴다).
