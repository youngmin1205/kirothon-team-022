# Quick Spec 가이드 (2-6) — 리허설 1 진행용

> 목표: 당일 첫 1시간(아이디어→채점→spec)을 **3명이 똑같이 따라 할 수 있게** 표준화한다.
> 선행물: 1-5 평가표(`docs/idea-scoring.md`), 2-2 steering, 이 문서.

---

## 0. 리허설 1 흐름 (총 60~70분)

| 단계 | 할 것 | 시간 |
|---|---|---|
| 1 | 각자 랜덤 아이디어 1개 (총 3개) | 사전 |
| 2 | `docs/idea-scoring.md`로 채점 → 1개 선정 | 10분 |
| 3 | **kiro-cli로 quick spec** (requirements→design→tasks) | **30분 타임박스** |
| 4 | tasks를 3명에게 분배 → 1-6 분담 방식 시험 | 10분 |
| 5 | 회고 (시간/크레딧/막힌 것/평가표 수정) | 10분 |

완료 기준: **spec 3파일 repo 커밋 + 회고 3줄** (`docs/practice/`).

---

## 1. Spec이란 (한 줄)
요구사항(requirements) → 설계(design) → 작업(tasks) 3단계 문서. **AI가 이 문서를 근거로 구현**한다. 문서가 좋을수록 결과가 좋다.

---

## 2. kiro-cli로 spec 시작하기

repo 루트에서:
```bash
kiro-cli
```

채팅에 아래처럼 **한 문단으로** 아이디어를 던진다 (예시: 복약 알림 앱):
```
"약 봉투를 사진으로 찍으면 복약 스케줄을 인식해서 알림을 만들어주는 웹 서비스"를
스펙으로 만들어줘. 해커톤 하루 데모가 목표라 범위를 최소 기능(MVP)로 좁혀줘.
스택은 steering(tech.md)을 따르고, LLM 호출은 Bedrock Converse를 쓴다.
먼저 requirements부터 보여주고, 내가 확인하면 design, 그 다음 tasks 순서로 진행해줘.
```

> IDE라면 상단 **Spec 메뉴**로 생성하면 requirements/design/tasks 파일이 자동으로 나뉘어 생성된다.

---

## 3. 단계별 체크 포인트

### requirements (요구사항)
- 사용자 스토리 + 수용 기준(EARS: "~할 때, 시스템은 ~해야 한다")
- ✅ 확인: **데모에서 보여줄 핵심 시나리오 1개**가 요구사항에 있는가? 없으면 추가.
- ✂️ 범위 밖 기능(로그인, 결제 등 데모에 불필요)은 "Out of scope"로 빼라고 지시.

### design (설계)
- 화면 → API → Bedrock 흐름, 데이터 형태, 에이전트 구성.
- ✅ 확인: 30분 안에 구현 가능한 수준인가? 과하면 "더 단순하게" 요청.

### tasks (작업 목록)
- 설계를 잘게 쪼갠 체크리스트.
- ✅ 확인: 각 task가 **1명이 20~40분에 끝낼 크기**인가? 3명에게 나눌 수 있게 독립적인가?

---

## 4. 30분 타임박스 운영 팁
- 각 단계에서 **완벽을 노리지 말 것.** "데모 시나리오를 완주할 뼈대"면 통과.
- 요구가 바뀌어 꼬이면 새로 쓰지 말고 **`/rewind`로 해당 지점으로 되돌린 뒤** 다시.
- 모델: 설계는 상위 모델, 단순 작업 쪼개기는 가벼운 모델로 섞어 크레딧 절약.
- spec 문서는 `.kiro/specs/<기능>/` 에 생성됨 → **커밋**해서 팀 공유.

---

## 5. tasks 분배 (단계 4)
- requirements/design는 공유 상태로 두고, tasks만 3명이 나눠 가진다.
- 분담 방식(1-6)을 여기서 시험: 기능별 / 레이어별 / 세션별 중 하나로 나눠보고 회고에서 평가.
- 겹치는 파일이 많으면 레이어별보다 기능별이 충돌이 적다.
