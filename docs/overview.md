# 이 레포가 무엇인지 — 전체 안내

> **이 문서 하나를 읽으면 레포 전체를 파악할 수 있게 쓴 설명서입니다.**
> 파일마다 "무엇인지 · 왜 있는지 · 언제 보는지"를 적었습니다.
> 바쁘면 1~3장만 읽으세요. 파일 단위 설명은 4장부터입니다.

---

## 1. 왜 이걸 만들었나

해커톤 조건이 이렇습니다.

- 주제가 **당일 10:40에 공개**됩니다. 미리 만들 수 없습니다
- 18:00 제출. 점심을 빼면 실제 개발은 **약 6시간**
- 3명이 한 레포에서 동시에 작업
- Kiro 사용이 필수

6시간은 코드를 쓰는 데는 충분합니다. Kiro가 빠르게 씁니다. 실제로 시간을 먹는 건 다른 네 가지입니다.

| 시간을 먹는 것 | 왜 |
|---|---|
| **결정 지연** | 무엇을 만들지 정하는 데 1시간 넘게 쓰면 개발 시간이 그만큼 줄어듭니다 |
| **환경 세팅** | 의존성 설치, 계정·모델 확인, "내 PC에서만 안 돼" |
| **통합 마찰** | 3명이 각자 만든 걸 마지막에 합치려다 안 붙음 |
| **마지막 1시간** | 영상·슬라이드·제출은 고정 비용인데 보통 처음 시도합니다 |

**이 네 개를 당일이 아니라 지금 없애는 것**이 이 레포의 목적입니다. 주제와 무관한 준비는 전부 미리 해 뒀습니다.

---

## 2. 무엇이 생겼나 (3줄)

1. **주제를 받으면 폴더 하나만 만들면 되는 앱 뼈대** — 화면 부품, 에이전트 루프, 자동 검증까지 동작 상태. **세 사람이 서로 기다리지 않게** 설계했습니다(3장)
2. **10분 안에 아이디어를 고르는 절차** — AI가 채점하고, 사람은 토론하지 않습니다 (리허설 97초)
3. **당일 분 단위 절차서** — 시간표·역할·명령어·막혔을 때 대응이 정해져 있어 당일에 논의하지 않습니다

여기에 더해, 리허설에서 **실제로 걸린 함정 7개**를 미리 찾아 고쳤습니다(9장).

## 3. 서로 기다리지 않게 만드는 방법

3명이 6시간 안에 뭔가를 완성하려면 **서로 기다리는 시간을 없애야 합니다.** 이게 그 방법입니다.

보통 화면을 만들려면 서버가 실제 데이터를 돌려줘야 합니다. 그래서 프런트 담당은 백엔드가 끝날 때까지 기다립니다. 6시간 중 그 대기 시간이 가장 아깝습니다.

### 핵심 흐름에 단계 이름을 붙입니다

여기서 "데모"는 제품의 **핵심 사용 흐름(happy path)** 을 말합니다. 사용자가 앱을 열어서 끝까지 가는 경로입니다.

```
전화가 온다 → 사기꾼이 말한다 → 압박한다 → 위험도가 오른다
→ 넘어간 순간 멈춘다 → 코치가 복기한다 → 결과를 보여준다
```

이 흐름을 6~8단계로 쪼개고 각 단계에 영문 이름을 붙입니다. 코드와 녹화 도구에서는 `beat`라고 부릅니다.

```
intro → incoming → hook → pressure → ask-info → freeze → coach → report
```

### 이름 하나가 네 곳에서 쓰입니다

`pressure` 단계를 예로 보면 이렇습니다.

**1. 서버** — `backend/features/sparring/mock.json`

```json
{ "id": "pressure", "text": "지금 끊으면 체포영장이 발부됩니다.", "data": { "riskScore": 55 } }
```

**2. 화면** — 그 단계가 끝나면 DOM에 남습니다

```html
<div data-beat="pressure" data-state="done">
```

**3. 자동 검사** — `pnpm smoke`가 이걸 기다립니다

```
[data-beat="pressure"][data-state="done"]   ← 안 나타나면 "pressure에서 멈췄다"
```

**4. 영상** — `deliverables/product.md`의 녹화 설정

```json
{ "id": "pressure", "sel": "[data-beat=\"pressure\"][data-state=\"done\"]", "caption": "압박이 시작됩니다" }
```

네 곳이 `pressure`라는 **같은 이름으로 서로를 찾습니다.** 그래서 이름을 한 곳(`product.md`)에서 정하고 나머지가 그걸 그대로 씁니다.

### 이름이 어긋나면

| 서버 | 화면 | 영상 설정 | 결과 |
|---|---|---|---|
| `pressure` | `step4` | — | smoke가 요소를 못 찾아 **실패로 뜹니다** (실제로는 잘 돌고 있는데) |
| `pressure` | `pressure` | `압박단계` | **녹화가 그 지점에서 멈춥니다** |

### 가장 큰 이득

11:25(product.md 직후)에 lead가 `mock.json`에 8단계 문구를 넣고 커밋하면, **프런트 담당은 그 순간부터 화면을 끝까지 만들 수 있습니다.** 백엔드가 Bedrock 프롬프트를 붙이는 동안 화면이 병렬로 완성됩니다.

그래서 기능이 하나도 없는 상태에서도 `#play` 한 번으로 흐름이 완주합니다. 11:30에 이미 영상을 뽑을 수 있고, 기능이 붙을 때마다 다시 뽑으면 됩니다.

### 덤으로 따라오는 것

같은 이름을 재사용하므로 추가 비용이 없습니다.

- `pnpm smoke`가 "어디까지 갔나"를 자동으로 확인합니다
- 17:00에 "다 됐나"가 단계 체크리스트로 판단됩니다
- 범위를 줄일 때 단계를 빼면 됩니다 (6~8개가 예산입니다)
- 영상 녹화가 단계마다 자동으로 자막을 붙입니다

### 안 쓰면

안 써도 됩니다. 대신 프런트가 백엔드를 기다리고, `pnpm smoke`는 "페이지가 떴다" 정도만 확인하고, 영상은 사람이 수동으로 멈춰 가며 찍습니다.

### 한계

**순차적인 흐름을 가정합니다.** 대시보드형이나 배치 처리형 아이디어라면 단계로 쪼개는 게 억지가 됩니다. 그 경우엔 느슨하게 쓰거나 버립니다.

[`idea-scoring.md`](idea-scoring.md)의 탈락 조건에 "데모 장면을 6~8단계로 못 쪼개면 탈락"을 넣은 것은 이 구조에 맞는 아이디어를 고르게 유도하는 것이기도 합니다. 6시간 안에 완주 가능한 형태라고 보기 때문이지만, **가능한 아이디어 범위를 좁히는 것도 사실입니다.**

### 개발 중에는 입력창, 검증·녹화는 `#play`

`features/sample/` 을 열면 **입력창이 먼저 보입니다.** 치면 실제 모델이 답합니다. 개발 중에 보는 화면이 실제 사용자가 보는 화면이어야 하기 때문입니다.

| | 쓰는 것 | 언제 |
|---|---|---|
| 개발 | 입력창 (`send`) | `pnpm dev` 로 띄우고 직접 대화하며 만든다 |
| 검증·녹화 | `#play` (`play`) | 체크포인트, `pnpm smoke`, 영상 |

화면은 두 층입니다. 기본은 **제품 화면**만 보이고, `?showcase=1` 을 붙이면 **계측 패널**(진행 단계·에이전트 흐름·점수)이 함께 나옵니다. `#play`·`#reset` 은 개발 바에 있고 녹화 때 숨깁니다.

`pnpm mock` 은 고정 경로입니다. mock 모드에서 자유 입력을 보내면 서버가 대본을 진행시키지 않고 안내를 돌려줍니다 — 입력이 무시된 것을 모델 오류로 오해하지 않게 하려는 것입니다. **자유 대화를 보려면 `pnpm dev` 로 띄웁니다** (AWS 호출이 발생합니다).

### `#play` 버튼이 왜 있는가

화면에 `id="play"` 버튼이 있고, 누르면 전 단계가 자동 재생됩니다. 쓰임이 네 가지입니다.

- 6시간 동안 **아무 때나 같은 흐름을 재현**할 수 있습니다 (통합 체크포인트 4회)
- `pnpm smoke`가 이 버튼을 눌러 **자동 검증**합니다
- 피칭 때 **무대에서 타이핑하지 않습니다**
- 영상 녹화 도구가 이걸 재사용합니다

재생이 끝나면 `#play` 의 `disabled` 가 풀리고, 그것이 "끝났다"는 신호입니다. 그래서 **사람이 한 줄 보낼 때는 `#play` 를 잠그지 않습니다.** 잠그면 녹화가 종료를 잘못 읽습니다.

### mock 모드가 왜 기본값인가

`USE_MOCK=1`이면 Bedrock을 호출하지 않고 고정 시나리오를 재생합니다. **AWS 자격증명도 네트워크도 없이 흐름이 완주합니다.**

최종 녹화는 live(실제 Bedrock)로 합니다. `#play` 가 `mock.json` 구간마다 적힌 `say` 를 모델에 보내므로 대본대로 찍힙니다. 피칭 중 라이브 호출 실패가 가장 흔한 사고라서 **무대 시연과 비상 녹화는 mock** 으로 합니다.

## 5. 파일 안내 — 실행 명령과 스크립트

### 루트 `package.json` — 모든 실행의 입구

```bash
pnpm bootstrap    # 의존성 설치 (전날 한 번, 277MB)
pnpm mock     # 데모 실행. Bedrock 호출 없음 → localhost:5173
pnpm dev      # 실제 모델로 개발
pnpm smoke    # 데모가 끝까지 도는지 자동 확인  ← 체크포인트마다
pnpm check    # lint · 타입 · 테스트 전체
pnpm build    # 프런트를 빌드해 backend/static_dist 로
pnpm start    # FastAPI 하나로 전체 서빙 (배포용 단일 프로세스)
```

포트는 **백엔드 8000, 프런트 5173 고정**입니다. 바꾸면 검증과 녹화가 깨집니다.

### 왜 "설치"가 필요한가 — `pnpm` 과 `uv`

`git pull` 로 받는 건 **우리가 쓴 코드**입니다. 그 코드는 남이 만든 라이브러리를 쓴다고 적어 놓은 상태입니다. 예를 들어 `frontend/package.json` 에 이렇게 있습니다.

```json
"dependencies": { "react": "^19.3.1" },
"devDependencies": { "vite": "^8.3.6", "typescript": "~7.0.2" }
```

이건 **"React 19와 Vite 8이 필요하다"는 주문서**입니다. React 자체는 레포에 없습니다.

| 도구 | 하는 일 | 읽는 주문서 | 받는 곳 |
|---|---|---|---|
| **`pnpm`** | Node.js 라이브러리를 받아옴 | `package.json` | `node_modules/` |
| **`uv`** | Python 라이브러리를 받아옴 | `pyproject.toml` | `.venv/` |

`pnpm` 은 패키지 매니저입니다. 같은 역할을 하는 게 `npm`(Node에 기본 포함), `yarn`, `pnpm` 셋인데 `tech.md` 에서 `pnpm` 으로 정했습니다. 같은 라이브러리를 복사하지 않고 링크로 재사용해서 디스크를 덜 씁니다.

`pnpm bootstrap` 은 위 두 명령을 한 번에 돌리는 단축 명령입니다.

**왜 git에 안 넣나**

`node_modules/` 와 `.venv/` 는 `.gitignore` 에 있습니다.

- **크기** — 277MB를 git에 넣으면 clone이 느려지고 히스토리가 망가집니다
- **누구나 같은 걸 받습니다** — 공개 저장소에서 내려받는 거라 레포에 담을 이유가 없습니다
- **OS마다 다릅니다** — 일부 라이브러리는 Mac용·Linux용 바이너리가 다릅니다

**안 돌리면**

```
$ pnpm mock
vite: command not found
ModuleNotFoundError: No module named 'fastapi'
```

앱이 뜨지 않습니다.

**크기**

| 명령 | 크기 | 누가 |
|---|---|---|
| `pnpm bootstrap` | **277MB** (`.venv` 109 + 프런트 154 + 루트 14) | 전원 |
| `pnpm bootstrap:deliverables` | **1.7GB** | 발표 산출물 담당(담당3)만 |

1.7GB는 전부 발표 도구입니다. Marp(슬라이드) · Mermaid(다이어그램) · Remotion(영상) · Playwright(녹화)인데 브라우저 엔진이 사실상 세 벌 들어옵니다. macOS에서만 동작하므로 나머지 두 사람은 받지 않습니다.

### `scripts/` — 점검과 자동화

| 파일 | 무엇인지 | 언제 |
|---|---|---|
| `preflight.sh` | **내 PC 준비 상태 점검.** 런타임 버전, kiro-cli, 에이전트 로딩, `.env`, 오프라인 캐시, 브라우저 라이브러리, 비밀키. 실패 항목만 출력. **AWS를 호출하지 않습니다** | 전날, 당일 아침 |
| `aws-check.sh` | **계정·리전·모델 확인.** 계정 확인 → 리전별 Claude 모델 조회 → (`--invoke` 시) 실제 호출로 되는 모델 확정 → EC2 권한 → `.env`에 붙일 두 줄 출력 | 계정을 받은 직후 |
| `score-ideas.sh` | **아이디어 채점 자동 실행.** 채점 기준 + 카드를 합쳐 kiro-cli로 1회 실행, 결과를 `idea-selection.md`로 저장 | 11:02~11:05 |
| `smoke.py` | **데모 완주 자동 확인.** uvicorn을 띄워 기능마다 `start`→`reply`×N을 돌리고 구간 누락을 잡음. `--ui`면 실제 브라우저로 `#play`까지 | 체크포인트마다 |
| `ui-check.mjs` | `smoke.py --ui`가 부르는 브라우저 검증. `#play` 클릭 → 구간 대기 → 스크린샷 | smoke가 자동 호출 |
| `scan-secrets.sh` | **비밀키 검사.** staged 변경에서 AWS 키·토큰·비밀번호 패턴을 찾음 | 커밋 전 |

> `aws-check.sh`는 **작성만 해 두고 실행하지 않았습니다.** 회사 계정(`mzc-aa`)이라 함부로 호출하지 않았습니다. 당일 주최 측 계정으로 돌리면 됩니다.

## 6. 파일 안내 — 앱 뼈대

### 구조 규칙: 기능 하나 = 폴더 하나

```
backend/features/<이름>/     ← 폴더를 만들면 main.py 가 자동으로 /api/<이름> 에 등록
frontend/src/features/<이름>/ ← registry.ts 에 한 줄 추가
```

이게 **3명이 같은 파일을 동시에 고치지 않게 하는 핵심**입니다. 각자 자기 폴더 안에서 끝냅니다.

### `backend/` — 서버

| 파일 | 무엇인지 | 당일 고치나 |
|---|---|---|
| `main.py` | 앱. `features/*/router.py`를 자동 등록. `/api/health`가 현재 모드와 구간 id를 보여줌 | ❌ lead만 |

### 원본에서 제가 바꾼 것

원본 프롬프트에 빈칸이 두 개 있었습니다. `준비된 뼈대: Bedrock 호출 래퍼, 오케스트레이터, 로컬 실행`과 `스택: <2-1에서 정한 것>`.

**이 빈칸이 D(하루 안에 구현) 점수를 직접 좌우합니다.** D는 가중치 ×2로 가장 무겁고, "준비물이 뼈대에 이미 있는 것뿐이면 3점"입니다. 뼈대 목록이 낡으면 **충분히 만들 수 있는 아이디어가 깎여서 탈락합니다.**

그래서 3장을 따로 만들어 **"있는 것 / 없는 것"을 표로** 적었습니다.

- 있는 것: LLM 래퍼, 에이전트 틀, mock 재생, 기능 플러그인, 화면 부품 11개, 한 줄 실행, 자동 검증, 발표 도구
- 없는 것: Knowledge Base, 음성(Transcribe/Polly), 파일 업로드, DB, 인증, AgentCore, 외부 API, 본격 차트, 배포

리허설에서 이게 실제로 작동했습니다. 보이스피싱은 준비물 3점(휴대폰 틀·게이지가 뼈대에 있음), 전세 계약은 2점(업로드가 없음)으로 정확히 갈렸습니다.

선정 출력에 **"데모 구간 6~8개"**를 추가한 것도 제가 바꾼 부분입니다. 그래야 선정 결과가 바로 `product.md`로 넘어갑니다.

## 9. 리허설에서 실제로 걸린 함정 7개

이게 사전 준비의 실질적 수확입니다. 전부 **당일에 만났으면 시간을 크게 잃었을 것들**입니다.

| # | 함정 | 어떻게 찾았나 | 조치 |
|---|---|---|---|
| 1 | **kiro-cli가 3.2.1인데 팀 문서는 2.2.2 기준** | 버전 확인 | 도구 이름(`fs_read`→`read`), 권한 필드(`toolsSettings`→`permissions`)가 전부 다름. 문서 전부 수정 |
| 2 | **자동 커밋이 이중으로 걸림** | 부수효과를 남기는 임시 훅을 심어 실측 | standalone 훅과 에이전트 내장 훅이 **동시에** 실행됩니다. `git add -A`가 두 번 돌면 남의 미완성 코드까지 커밋됩니다 → 양쪽에서 제거 |
| 3 | **`--no-interactive`로 돌리면 파일을 못 씀** | spec 생성을 스크립트로 시도 | 승인할 사람이 없어 4번 재시도 후 포기. **227초와 크레딧만 날렸습니다** → `--trust-tools` 필요 |
| 4 | **`pnpm install`이 멈춤** | 프런트 설치 | pnpm 12가 esbuild 빌드 스크립트를 거부. `pnpm-workspace.yaml`에 허용 명시 (`package.json`의 `pnpm` 필드는 더 이상 안 읽힘) |
| 5 | **타입 검사 실패** | `tsc -b` | vitest 3이 Vite 7 타입을 끌어와 Vite 8과 충돌 → vitest 5로 올림 |
| 6 | **WSL/Linux에서 영상 녹화 불가** | 녹화 시도 | chromium이 `libasound.so.2` 부족으로 실행 안 됨 (소리가 아니라 로드 시점 의존성) |
| 7 | **다이어그램 도구가 macOS 전용** | 다이어그램 생성 시도 | `puppeteer.json`에 Chrome 경로가 `/Applications/...`로 하드코딩 |

6·7 때문에 **발표 산출물은 담당3(macOS)이 담당**하는 것으로 정리했습니다. 그 노트북에 의존한다는 위험은 `handoff-11-13.md`에 적어 뒀습니다.

추가로, 저장할 때마다 모델을 호출하는 비밀키 검사 훅을 발견해 `scripts/scan-secrets.sh`로 옮겼습니다. 그 훅의 트리거(`PostFileSave`)는 출력이 세션에 전달되지 않아 **경고가 사람에게 보이지도 않는 상태**였습니다.

## 10. 내가 지시한 것과 달라진 결정들

제가 중간에 판단을 바꾼 지점입니다. 근거를 남겨 둡니다.

| 처음 안 | 최종 | 왜 바꿨나 |
|---|---|---|
| 기능 수직 분할 (각자 기능 하나를 세로로) | **레이어별 + 기능 폴더** | 수직 분할은 두 사람이 모두 `frontend/`에 들어가 공용 스타일을 건드립니다. 레이어별은 경로가 완전히 분리되고, API 형식을 먼저 고정하면 기다림도 없습니다 |
| 에이전트 4개 (`lead`/`frontend`/`backend`/`reviewer`) | **2개 (`build`/`review`)** | 레이어별 규칙은 `fileMatch` steering이 이미 합니다. 3명이 각자 clone으로 일하므로 경로 권한이 막아주는 게 적습니다. 에이전트가 많으면 당일 아침에 깨질 표면이 늘어납니다 |
| 권한을 `permissions.rules`로 경로 차단 | **`tools` 목록으로 제한** | `permissions`에서 확인된 capability는 `fs_read`·`skill`뿐입니다. 추측해 쓰면 validate는 통과하지만 실제로 안 걸립니다 — 기존 `allowedTools`가 정확히 그 경우였습니다 |
| `.phone .screen` 구조를 필수 계약으로 | **모바일 형태일 때만** | 녹화 도구 제약이 아키텍처를 끌고 가던 것을 바로잡았습니다. `#play`는 테스트 가능성 때문에 남겼습니다 |
| 영상·슬라이드 경로를 전부 검증 | **1회 시도만, 담당3에게 이관** | 제출 요건에 영상이 없을 수도 있고, Linux에서 막혔습니다 |
| `Makefile` | **루트 `package.json` 스크립트** | Make는 Windows에 기본으로 없고 탭 문자에 민감합니다. `deliverables/`가 이미 npm 스크립트를 씁니다 |
| 결정 기록·브랜치 비교 장치 | **제거** | 과했습니다 |
| 데모 화면이 기본, 입력창은 나중 | **입력창이 기본, 대본 재생은 그 위에 얹음** | `features/sample/`이 "대본 재생 쇼케이스"였습니다. 입력창이 없어서(`PhoneFooter`를 만들어 놓고 연결하지 않았습니다) 당일 이 폴더를 복사하면 입력 없는 화면에서 시작하게 됩니다. 개발 중에 보는 화면이 실제 사용자가 보는 화면이어야 합니다 |
| 적응적 반응을 **코드**가 결정 (키워드 분류 → 상태 전이) | **모델이 결정하고 코드가 제약** (`escalate` 도구 + ±1칸 제한) | 제가 안전성에 너무 기울었습니다. 코드가 전이를 정하면 모델이 하는 일이 "문장 표현"뿐이어서 "에이전트가 무엇을 판단하나"에 답할 게 없습니다. 전이 판단을 모델에게 주고 코드는 범위만 막으면, 모델이 적은 전이 근거(`why`)를 화면에 띄울 수 있습니다 — 규칙 기반에서는 나오지 않는 출력입니다. 재현성이 필요한 셋(위험도 숫자·`freeze` 판정·한 칸씩 오르기)만 코드가 들고 있습니다. 기록 위치: `docs/practice/spec-example-sparring/design.md` |
| RAG(Knowledge Base)로 사기 수법을 검색 | **시스템 프롬프트에 사다리로 넣음** | 사기 수법은 검색할 지식이 아니라 행동 규칙이고, 전체가 300~500단어로 프롬프트에 들어갑니다. 코퍼스가 크지도 자주 바뀌지도 않아 RAG의 이득이 없고, S3·색인·청킹에 몇 시간을 쓰면서 사용자가 보는 반응은 나아지지 않습니다. 검색 결과가 턴마다 흔들려 데모 재현성도 떨어집니다 |
