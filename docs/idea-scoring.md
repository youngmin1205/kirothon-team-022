# 아이디어 채점표 (AI 채점용)

> **사람은 아이디어 카드만 쓰고, 채점과 선정은 AI(kiro-cli)가 합니다. 토론은 하지 않습니다.**
> 공식 심사 기준은 모릅니다. 과거 Kiro 해커톤의 공통 축(가치 · Kiro 활용 깊이 · 독창성)에 "하루 안에 구현 가능한지"를 더해서 봅니다.
>
> 당일 실행: `./scripts/score-ideas.sh` → 결과가 `docs/idea-selection.md`에 저장됩니다.

---

## 1. 아이디어 카드 (사람이 씀, 1개당 2분)

AI는 카드에 적힌 것만 보고 채점합니다.

**모든 칸은 "최소 데모 버전" 기준으로 씁니다.** 하루 안에 만들 가장 작은 버전 하나만 적고, 더 하고 싶은 건 "확장" 칸에 따로 적습니다. 확장은 K(활용 깊이)에서 2점까지만 받고 D(구현)에는 들어가지 않습니다.

```
## 아이디어: <이름>
- 사용자: 누가 쓰는지
- 문제: 지금 뭐가 불편한지 (1문장)
- 해결: 최소 데모 버전으로 뭘 만드는지 (1문장)
- 데모 장면: 입력 → 화면에 보이는 결과 (1문장)
- 필요한 것: 최소 데모 버전에 꼭 필요한 데이터 / 외부 API / 권한 / 처음 쓰는 AWS 서비스·라이브러리 (없으면 "없음")
- (선택) 확장: 시간이 남으면 붙일 AWS·Kiro 기능 (예: "규칙 검사를 AgentCore Policy로 교체")
- (선택) 축소안: 시간이 모자라면 뭘 빼고 뭘 남기는지 (1문장)
```

- 필수 칸(사용자·문제·해결·데모 장면·필요한 것)이 비면 그 칸에 걸린 항목은 1점
- **데모 장면은 통과 조건입니다.** 형식(`행동 1개 → 화면에 뜨는 것`)이 안 맞으면 채점하지 않고 "탈락: 데모 장면 없음"으로 표시

**데모 장면 쓰는 법:** `사용자가 하는 행동 1개 → 화면에 뜨는 것` (명사로 끝냄)

- ✅ "AWS 비용 CSV를 올리면 → 서비스별 비용 막대그래프 + '줄일 수 있는 3가지' 카드가 뜸"
- ✅ "회의 녹음을 넣으면 → 담당자별 할 일이 칸반 보드에 자동으로 채워짐"
- ✅ "장애 로그를 붙여넣으면 → 원인 후보 3개가 확률 순으로 뜨고, 클릭하면 근거 로그가 하이라이트됨"
- ❌ "AI가 비용을 분석해줌" (뭘 넣는지, 화면에 뭐가 보이는지 없음)
- ❌ "챗봇이 답변함" (결과가 텍스트뿐 → B에서 1점)

> 💡 **데모 장면은 그대로 다음 단계로 넘어갑니다.** 선정된 카드의 데모 장면을 6~8개 구간으로 쪼개면 그게 `.kiro/steering/product.md`의 데모 구간이 되고, 화면 신호·mock 시나리오·영상 구간이 모두 같은 id를 씁니다. 그래서 데모 장면을 구체적으로 쓸수록 이후가 빨라집니다.

## 2. 채점 기준 (1~3점 × 가중치, 만점 15)

| # | 항목 | 가중치 | 3점 | 2점 | 1점 |
|---|---|---|---|---|---|
| A | 문제·가치 | ×1 | 사용자와 문제가 구체적이고, 많은 사람이 겪는 문제임 | 사용자나 문제 중 하나가 막연함 | 누가 왜 쓰는지 안 보임 |
| B | 참신함 | ×1 | 해커톤에서 흔한 유형이 아님 | 흔한 유형에 뚜렷한 차별점 1개 | 흔한 유형 그대로 (RAG 챗봇, 문서 요약, 회의록 정리, 텍스트만 나오는 챗봇 등) |
| K | Kiro·AWS 활용 깊이 | ×1 | 최소 데모 버전의 핵심이 Bedrock 단순 호출 너머의 AWS·Kiro 기능에 기대고, 그게 데모 장면에 보임 (예: AgentCore, Knowledge Base, Transcribe, Kiro MCP·hooks) | Bedrock 호출이 핵심 / 또는 고급 AWS·Kiro 기능이 "확장"에만 있음 | LLM·AWS 없이도 되는 앱 |
| D | 하루 안에 구현 | **×2** | 아래 **준비물**과 **난이도** 중 낮은 점수 | | |

### D 세부: 준비물과 난이도 중 낮은 점수

"뼈대"는 아래 3장에 적힌 것만 뜻합니다.

| 점수 | 준비물 ("필요한 것" 칸 기준) | 난이도 (핵심 기능 기준) |
|---|---|---|
| 3 | "없음" 또는 뼈대에 이미 있는 것뿐 | LLM 호출 + 일반 화면·저장(입력 폼, 표, 목록)으로 됨 |
| 2 | 뼈대 밖 준비물이 있지만 **전부** 당일 30분 안에 준비됨 (개수 무관): 우리 AWS 계정에서 바로 켜지는 서비스, 키가 바로 나오는 무료 API, 직접 만드는 샘플 데이터 | 처음 쓰는 서비스·라이브러리 1개가 핵심이거나, LLM 결과 품질이 데모 성패를 가름 (프롬프트 튜닝 필요) |
| 1 | 하나라도 30분 안에 안 됨: 승인·심사 대기(모델 접근 신청, 쿼터 증가, 외부 API 심사), 카드 결제가 필요한 외부 유료 API, 구할 수 없는 실데이터 | 연구 수준 처리가 핵심 (사진→평면도·3D, 실시간 영상·음성 스트리밍, 정밀 수치·좌표 정확도) 또는 처음 쓰는 것 2개 이상 |

- **AWS 서비스 요금은 "유료 API"로 보지 않습니다.** Bedrock·Transcribe 등 우리 계정 안에서 과금되는 건 준비물 2점 기준(바로 켜지는지)으로만 봅니다
- "필요한 것"에 확장 칸의 기능은 넣지 않습니다. AgentCore를 최소 버전에 쓰면 K는 오르고 D는 내려갑니다 (뼈대에 미리 넣어 두면 D는 안 내려감)

**동점 처리:** 1등과 2등 차이가 **1점 이하**면 동점으로 봅니다. 아래 순서로 가리고, 끝까지 같으면 마지막 규칙으로 무조건 끝냅니다.

1. D(하루 안에 구현) 높은 쪽
2. A(문제·가치) 높은 쪽
3. B(참신함) 높은 쪽
4. 축소안이 적힌 쪽
5. 그래도 같으면 카드 목록에서 먼저 나온 쪽

## 3. 뼈대에 있는 것 / 없는 것 (D 점수의 기준)

> ⚠️ **이 목록이 D 점수를 좌우합니다.** 뼈대가 바뀌면 여기를 먼저 고칩니다.
> 확인 방법: `pnpm smoke` 가 통과하면 아래 "있는 것"은 실제로 동작하는 상태입니다.

### 있는 것 — "필요한 것"에 적혀도 준비물 3점

| 영역 | 내용 |
|---|---|
| LLM | Bedrock Converse 래퍼, tool use(도구 호출) 루프, 실패 시 mock 폴백 |
| 에이전트 | 오케스트레이터 + 서브에이전트 틀, 세션 대화 이력(메모리) |
| 데모 안정성 | `USE_MOCK=1` 고정 시나리오 재생 → 네트워크·자격증명·크레딧 없이 데모 완주 |
| 구조 | 기능 = 폴더 하나 (백엔드 `backend/features/<이름>/`, 프런트 `frontend/src/features/<이름>/`) 자동 등록 |
| 화면 | React 셸, 대화 입력창(Enter 전송), 데모 자동 재생(`#play`), 구간 진행 신호 |
| **입력** | 텍스트 한 줄 · **폼 값·좌표 등 구조화 입력(`payload`)** · **사진·CSV·PDF 첨부(`files`, 3개·5MB, 형식 검사 포함)**. 업로드 UI 부품(`FilePick`)도 있음 |
| **출력** | 턴마다 **구조화 값(`data`)** 을 함께 받아 표·카드·게이지를 그릴 수 있음. mock 은 `mock.json` 의 `beats[].data`, 실제 모델은 응답 JSON 에서 뽑음 |
| 화면 부품 | 카드 · 버튼 · 상태 칩 · 단계 타임라인 · **표** · 숫자 강조 · 진행바/점수 게이지 · 에이전트 흐름도 · 로그 패널 · 토스트 · 휴대폰 틀 · 대화 버블 · 입력창 · 파일 선택 |
| 실행 | `pnpm bootstrap` / `dev` / `mock` / `build` / `start` 한 줄 실행, 포트 고정(8000·5173) |
| 검증 | `pnpm smoke`(데모 완주 자동 확인), `pnpm check`(lint·타입·테스트) |
| 발표 | 슬라이드·영상·다이어그램 도구 (담당3, **macOS 에서만 동작**) |

### 없는 것 — 쓰려면 준비물 2점 이하

| 영역 | 비고 |
|---|---|
| Knowledge Base / RAG 색인 | 문서 업로드·색인 파이프라인 없음 |
| Transcribe · Polly (음성 입출력) | 실시간 스트리밍은 난이도 1점 |
| 파일 **저장**(S3 등) | 받아서 그 턴에 쓰는 것까지만 된다. 저장·재조회 경로는 없음 |
| 데이터베이스 | 메모리뿐. 재시작하면 날아감 |
| 로그인·인증 | 없음 |
| AgentCore | 없음 |
| 외부 API 연동 | 공통 클라이언트 없음 |
| 본격 차트 라이브러리 | 막대·게이지·표는 부품으로 있지만 그 이상은 없음. 이미지 위 오버레이·지도는 없음 |
| 배포 | 로컬 실행이 기본. URL 이 필요하면 터널 1~2분 (미검증) |

> 📌 **전략 메모:** K(활용 깊이)는 ×1, D(구현)는 ×2 입니다. 그래서 "없는 것"에 있는 AWS 기능을 **미리 뼈대에 넣어 두면** 그 기능을 쓰는 아이디어가 K를 올리면서 D를 잃지 않습니다. 남은 준비 시간에 하나를 고를 수 있다면 후보는 Knowledge Base 또는 Transcribe 입니다. (현재는 넣지 않았습니다)
>
> 11/13 에 같은 이유로 **입력(파일·구조화)과 출력(구조화 값)** 을 뼈대에 넣었습니다. 근거와 측정은 [`skeleton-generality-audit.md`](skeleton-generality-audit.md) 에 있습니다.

## 4. AI 채점 프롬프트

`./scripts/score-ideas.sh` 가 이 파일의 1~3장과 `docs/idea-cards.md` 를 합쳐 아래 프롬프트로 실행합니다. 손으로 붙여넣을 필요는 없습니다.

```
너는 해커톤 아이디어 심사자야. 아래 [팀 컨텍스트]와 [채점 기준]만 써서 [아이디어 카드]들을 채점하고 1개를 골라.

규칙
- 카드에 적힌 내용만 근거로 써. 추측해서 점수 올리지 마. 필수 칸이 비었으면 그 칸에 걸린 항목은 1점.
- 데모 장면이 "행동 1개 → 화면에 뜨는 것" 형식이 아니면 채점하지 말고 "탈락: 데모 장면 없음"으로 적어.
- 모든 채점은 "최소 데모 버전" 기준. "확장" 칸의 기능은 K에서 최대 2점까지만 반영하고, D에는 넣지 마.
- D는 준비물 점수와 난이도 점수를 각각 매기고, 낮은 쪽을 D로 써. 근거에 둘 다 적어 (예: "준비물 3 / 난이도 1 → D=1").
- 준비물 점수는 [뼈대] 목록을 기준으로 판단해. "있는 것"에 해당하면 3점이고, "없는 것"에 해당하면 30분 안에 준비되는지로 2점·1점을 가려.
- AWS 서비스 요금(Bedrock, Transcribe 등)은 유료 API로 보지 마. 승인 대기나 외부 유료 결제가 필요할 때만 준비물 1점.
- 항목마다 점수 + 근거 1줄 (카드 문구를 인용).
- 합계 = A + B + K + 2D (만점 15).
- 1등과 2등 차이가 1점 이하면 D → A → B → 축소안 있는 쪽 → 카드 목록에서 먼저 나온 쪽 순서로 골라. 어느 단계에서 갈렸는지 적어.
- 마지막에 다음을 적어:
  1. 선정 / 백업
  2. 선정 아이디어의 데모 구간 6~8개를 표로 (열: # · id(영문 소문자) · 사용자 발화 1줄 · 화면에 보이는 것 1줄). 사용자 발화는 그 구간 직전에 사용자가 입력하거나 누르는 것을 한 문장으로 쓴다. 1번 구간은 시작 화면이라 비운다. 이 표가 product.md 와 mock 시나리오의 뼈대가 되고, 발화는 live 녹화 때 실제 모델에 들어간다.
  3. 선정 아이디어의 3명 분업안 (프론트 · 백엔드 · 에이전트 각 1줄, 서로 기다리지 않고 동시에 시작할 수 있게). 이렇게 나눌 수 없으면 백업을 선정으로 올리고 이유를 적어.
  4. 선정 아이디어의 가장 큰 리스크 1개
  5. 데모의 핵심 숫자가 live 모델로 재현되는가. 모델이 카드와 다르게 판단하면 어떤 숫자가 나오는지, 재현하려면 프롬프트에 어떤 제약이 필요한지 1줄

출력: 표 1개 (아이디어 | A | B | K | D(준비물/난이도) | 합계) → 항목별 근거 → 동점 처리 → 선정·백업·데모 구간·분업안·리스크·live 재현
파일은 수정하지 마. 결과만 출력해.

[팀 컨텍스트]
- 3명, 해커톤 1일 (구현 약 6시간, 11:00~18:00 중 점심 1시간 제외)
- 17:00 기능 추가 중단, 18:00 제출
- 스택: React + Vite + TypeScript (프런트) / Python + FastAPI (백엔드) / Bedrock Converse API 를 boto3 로 직접 호출
- 실행: 로컬. 배포는 기본적으로 안 함
- 데모는 USE_MOCK 모드로 재생할 수 있어야 함 (라이브 LLM 호출 실패 대비)

[뼈대]
<idea-scoring.md 3장: 있는 것 / 없는 것 표>

[채점 기준]
<idea-scoring.md 2장: 채점 기준 표 + D 세부 표 + 동점 처리>

[아이디어 카드]
<docs/idea-cards.md 전체>
```

## 5. 진행 방식 (10분 타임박스)

1. **카드 작성 (각자 2분, 동시에):** 1인 1~2개를 `docs/idea-cards.md` 에 씀. 최소 데모 버전 기준
2. **AI 채점 (3분):** `./scripts/score-ideas.sh` 실행
3. **확인 (2분):** 근거만 봅니다. 사실과 다른 근거가 있으면 그 칸만 고쳐서 1번 다시 돌립니다 (최대 1번)
4. **선정 (1분):** AI가 고른 1등을 바로 채택. 다시 논의하지 않습니다
5. **기록:** 결과가 `docs/idea-selection.md` 에 저장됩니다. 커밋합니다

> 사람이 할 수 있는 건 "근거가 사실과 다름" 지적뿐입니다. "그래도 이게 더 끌리는데"는 받지 않습니다.

**바로 다음 단계:** 선정 결과의 "데모 구간 6~8개"를 `.kiro/steering/product.md` 에 옮깁니다. 거기서부터 spec·화면·mock·영상이 같은 구간 id를 공유합니다.

## 6. 리허설 후 점검 (회고에 적음)

- 10분 안에 끝났는지
- 같은 카드로 2번 돌렸을 때 1등이 바뀌는지 → 바뀌면 그 항목의 점수 정의를 더 구체적으로 고침
- AI 결과가 셋의 직감과 크게 달랐는지 → 다르면 가중치를 볼지, 카드를 더 잘 쓸지 정함
- 카드에서 자주 비는 칸이 있었는지
- 모든 카드가 같은 점수를 받은 항목이 있는지 → 있으면 변별력 없음, 정의를 고치거나 통과 조건으로 바꿈
- **3장 뼈대 목록이 실제와 맞는지** (틀리면 D 점수가 전부 틀어짐)
