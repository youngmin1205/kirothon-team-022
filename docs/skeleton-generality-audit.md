# 뼈대 범용성 감사 (11/13)

> **질문:** 사전 준비된 뼈대가 리허설에 쓴 예시 아이디어(보이스피싱 스파링)에 맞춰진 것인가,
> 어떤 주제가 와도 쓸 수 있는 범용 준비인가.
>
> **방법:** 입출력 모양만 다르고 문제·가치는 비슷한 카드 4개로 채점을 돌려, 점수가 아이디어의
> 질이 아니라 뼈대가 그 모양을 받는지에 따라 갈리는지 본다. 고친 뒤 같은 카드로 다시 돌린다.

## 결론

**뼈대 자체는 아이디어 중립이었다.** 공용 코드에 리허설 주제의 흔적은 주석과 예시 문구뿐이고
로직에는 없다. 기능 자동 등록, 구간 재생, 검증·녹화 계약, Bedrock 래퍼는 주제와 무관하다.

**다만 입력과 출력의 모양이 "텍스트 대화형"으로 좁혀져 있었다.** 이건 특정 아이디어가 아니라
"입력이 파일인 아이디어 전부", "결과가 숫자·표인 아이디어 전부"에 걸리는 문제여서 고쳤다.

고친 뒤, 업로드형 아이디어의 D 준비물 점수가 2점에서 3점으로 올라갔고(보조 측정), 대조군
(음성 스트리밍)은 움직이지 않았다. 즉 **고친 것이 의도한 범위에만 작용했다.**

## 1. 아이디어와 무관한 부분 (그대로 쓸 수 있다)

| 부분 | 근거 |
|---|---|
| 기능 자동 등록 | `backend/main.py` 의 `discover_features()` 가 폴더 이름만 보고 등록. 프런트는 `src/features/registry.ts` 한 줄 |
| 구간(beat) 재생 | `backend/core/mock.py` 는 `id` · `text` · `delayMs` · `data` 만 안다. 내용은 모른다 |
| 검증·녹화 계약 | `#play` 와 `data-beat`/`data-state`. `scripts/ui-check.mjs` 는 product.md 없이 구간 id 만 받게 일부러 분리해 뒀다 |
| Bedrock 래퍼 | `core/bedrock.py` 의 도구 루프와 실패 시 mock 폴백. 모델·프롬프트만 갈아끼운다 |
| 세션 | `core/session.py` 의 `state: dict` 가 기능별 임의 상태를 받는다 |
| 화면 껍데기 | `app/Shell.tsx` 의 `layout` 이 `phone` · `browser` 둘을 받고, 제품 화면과 계측 패널이 분리돼 있다 |

리허설 주제의 흔적은 다음 세 곳의 **주석·예시 문구**뿐이다. 동작에는 영향이 없다.
`core/mock.py` 의 JSON 예시, `ui/phone.tsx` 의 출처 주석, `ui/primitives.tsx` 의 출처 주석.

## 2. 고친 구멍 둘

### 구멍 1 — 백엔드가 보낸 구조화 결과가 화면까지 가지 못했다

봉투에 `state` 가 있고 `TurnResponse` 타입에도 있었지만 `useDemo` 의 `absorb()` 가 읽지 않았고,
mock 쪽은 `next_beat()` 가 돌려준 `data` 를 `_mock_turn` 이 버렸다. 그래서 숫자·표·게이지를
그릴 공식 경로가 없었다. 채점표가 "텍스트만 나오는 결과는 B 1점"이라고 적어 둔 것과 어긋났다.

고친 방식:

- `core/bedrock.py` — `Result.data` 추가, `as_dict()` 에 포함
- `core/agent_loop.py` — `_mock_turn` 이 `beat["data"]` 를 그대로 싣는다
- 실제 모델 모드도 같은 모양이 되게 `parse_json_block()` 을 추가했다. 응답 텍스트의 JSON 블록을
  뽑아 `data` 에 넣고, 못 뽑으면 텍스트만 보낸다(예외를 던지지 않는다)
- `app/useDemo.ts` — `data`(마지막 턴) · `dataByBeat`(구간별) · `serverState`(봉투의 state) 를 내준다

### 구멍 2 — 입력이 "텍스트 한 줄"로 고정돼 있었다

`ReplyIn.text`(1~2000자)와 `api.reply(feature, sid, text)` 가 전부였다. 파일·폼 여러 칸·좌표를
보낼 자리가 없었고, `idea-scoring.md` 3장이 파일 업로드를 "없는 것"으로 분류하고 있어서 D는
×2 가중치를 받는다. 즉 **사진·CSV·녹음·PDF 를 받는 아이디어는 카드를 잘 써도 구조적으로 깎였다.**

고친 방식:

- `core/attachments.py`(신규) — JSON 안의 base64 를 받아 개수(3개)·크기(`ATTACHMENT_MAX_MB`, 기본
  5MB)·형식 화이트리스트를 신뢰 경계에서 검사한다. 파일 이름의 경로와 제어문자를 털어낸다.
  이미지·PDF·텍스트를 Converse 블록으로 바꾸는 변환도 여기 있다
- `features/sample/router.py` — `payload`(구조화 입력)와 `files`(첨부)를 **선택 필드로** 추가.
  `text` 는 첨부만 보내는 경우를 위해 비어도 되게 풀었다
- `core/agent_loop.py` — `Agent.run(session, text, files)` 가 이미지·문서 블록을 같은 메시지에 넣는다
- `lib/files.ts` · `ui/FilePick.tsx` · `lib/api.ts` · `useDemo.send(text, input)` — 프런트 경로
- mock 모드에서 첨부가 오면 대본을 진행시키지 않고 **무엇을 받았는지 요약해 안내로** 돌려준다.
  업로드가 서버에 닿았는지 화면에서 확인할 방법이 없으면 "업로드가 안 됐다"고 오해한다

기존 계약은 하나도 바꾸지 않았다. `#play`, `data-beat`/`data-state`, 포트, 응답 봉투의 기존 필드,
mock 자유입력 안내가 그대로다. 모두 **더하기만** 하는 변경이다.

### 덧붙여 — 표 부품

두 측정 모두 1·2위가 대시보드형·대화형으로 나왔다. 결과가 목록·순위인 기능이 바로 쓸 수 있게
`ui/primitives.tsx` 에 `DataTable` 을 넣었다. 열을 주지 않으면 서버가 보낸 배열의 첫 행 키를
그대로 머리로 쓴다. 그래서 `mock.json` 의 `data` 에 배열만 적어 두면 표가 채워진다
(`features/sample/mock.json` 의 `result` 구간이 예시다). 채점 점수에 영향은 없다 — 화면 부품은
이미 "있는 것"이었다. 당일 조립 시간을 줄이려는 것이다.

## 3. 고치지 않은 것

| 안 고친 것 | 이유 |
|---|---|
| 이미지 위 오버레이·격자·지도 부품 | "무엇 위에 무엇을 겹치는가"가 아이디어마다 달라 미리 만들면 당일 고쳐 쓰게 된다 |
| 파일 **저장**(S3) | 받아서 그 턴에 쓰는 것까지가 데모에 필요한 전부다 |
| 음성 입출력(Transcribe·Polly) | 실시간 스트리밍은 채점표에서 난이도 1점이다. 뼈대에 넣어도 그 점수는 안 올라간다 |
| Knowledge Base / RAG, AgentCore, DB, 로그인 | 범위 밖. 필요하면 K를 올리는 대신 D를 내주는 선택이다 |
| Rekognition, 좌표 변환, Web Audio, 군중 샘플 사진 | **특정 아이디어 전용.** 당일 기능 폴더에서 해결할 것이고, 뼈대에 없는 게 흠이 아니다 |

## 4. 측정 결과

### 본 측정 — 같은 카드 4개, 고치기 전과 후

| 카드 (유형) | 전 | 후 | D 준비물 근거의 변화 |
|---|---|---|---|
| 붐빔 지도 (파일 입력) | 9 (D=1, 준비물 2/난이도 1) | 9 (D=1, 준비물 2/난이도 1) | **"업로드 처리가 뼈대에 없음" → "업로드 처리는 뼈대에 있음, 남은 건 샘플 사진"** |
| 위험 구역 브리핑 (대시보드) | 13 (D=3) | 13 (D=3) | "표·게이지 부품" → **"뼈대의 구조화 출력(`data`)과 표·게이지 부품"** |
| 대처 리허설 (대화형) | 11 (D=2) | 11 (D=2) | 변화 없음 (준비물 "없음") |
| 통화 실시간 경고 (**대조군**) | 10 (D=1) | 10 (D=1) | **변화 없음** — 의도한 대로 |

총점은 넷 다 그대로다. 바뀐 것은 **점수가 깎이는 이유**다. 「붐빔 지도」가 여전히 D=1 인 것은
D가 `min(준비물, 난이도)` 이고, 그 카드의 난이도 1점은 뼈대와 무관한 사유(구역별 밀집도의
좌표 정밀도)에서 오기 때문이다.

> 고친 뒤 채점이 난이도 1의 근거로 "이미지 위 오버레이·지도는 없음"을 인용했다. 이 문장은
> 이번에 3장에 **새로 적은 것**이다. 뼈대 목록을 정확하게 쓰면 그만큼 정확하게 깎인다.

### 보조 측정 — 난이도 요인을 뺀 업로드형

본 측정이 난이도에 묶여 업로드의 효과를 보여주지 못했으므로, 좌표 정밀도 같은 요인이 없는
업로드형 카드로 한 번 더 재 봤다.

| 카드 | D | 준비물 근거 |
|---|---|---|
| 영수증 안전 점검 (사진 업로드 → 표·배지) | 2 (**준비물 3** / 난이도 2) | "뼈대의 `files`(3개·5MB, 형식 검사)와 `FilePick` 로 이미 있어 준비물 3" |

고치기 전이라면 같은 카드가 「붐빔 지도」와 같은 이유로 준비물 2점을 받았을 것이다.
**업로드형 아이디어가 더는 뼈대 때문에 깎이지 않는다**는 것이 이 측정의 결론이다.

### 측정의 한계

- 채점은 모델 호출이라 비결정적이다. 각 조건을 **한 번씩만** 돌렸다. 총점의 ±1 은 신호가 아니다
- 그래서 총점보다 **근거 문구가 무엇을 인용하는지**를 봤다. 그쪽이 뼈대 목록과 직접 연결된다
- 카드 4개는 유형 대표일 뿐이다. 당일 주제가 이 네 모양 밖일 수 있다

## 6. 당일 이것이 무엇을 바꾸는가

- 입력이 파일인 아이디어를 **아이디어 선정 단계에서 불리하지 않게** 받을 수 있다
- `mock.json` 의 `beats[].data` 에 숫자를 적으면 백엔드 로직 없이 **숫자가 바뀌는 화면**을
  끝까지 만들 수 있다. 프런트가 백엔드를 기다리는 구간이 줄어든다
- 실제 모델 모드에서도 같은 자리(`data`)로 숫자가 오므로, 프롬프트에 "수치는 JSON 으로 같이
  달라"만 적으면 화면 코드를 바꾸지 않는다

## 7. 다음에 준비 시간이 남으면

채점표 3장의 전략 메모와 같은 판단이다. K를 올리면서 D를 지키려면 "없는 것"에서 하나를 골라
뼈대에 넣는다. 지금 후보는 **Knowledge Base** 또는 **Transcribe(파일 업로드 기반, 스트리밍 아님)**
이다. 업로드 경로가 생겼으므로 Transcribe 쪽은 전보다 적게 든다.
